# 課程專有名詞範本研究

研究日期：2026-10-29。本次只研究，不加入範本 UI 或更動辨識參數。

## 結論

可先整合現有的「講題前導提示」與「熱詞文字檔載入」，讓老師儲存、套用不同課程的設定；不需要加入新辨識服務或上傳教材。範本應區分講題情境與專有名詞，不能把所有術語都當成強制替換規則。

## 後端差異

| 後端 | 可採用的方式 | 應注意的限制 |
| --- | --- | --- |
| CPU／CUDA 標準推論 | 現有 `initial_prompt` 與 `hotwords` | 前導提示主要作用於第一個視窗；熱詞不是保證拼字正確的字典 |
| CPU／CUDA 批次推論 | 同樣傳送提示與熱詞 | 上游對各音訊視窗使用提示，效果不能直接等同標準模式 |
| MLX 原生推論 | 使用 `initial_prompt` 表達講題及少量重要術語 | 沒有可直接對等傳入的原生 `hotwords` 介面；現有熱詞只參與後處理，不會引導聲學辨識 |

依據：[faster-whisper 官方實作與參數說明](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py)、[mlx-whisper 官方轉錄介面](https://github.com/ml-explore/mlx-examples/blob/main/whisper/mlx_whisper/transcribe.py)。標準及批次的提示套用位置不同，正式實作前應針對專案固定的套件版本再次驗證。

## 建議的後續設計

1. 範本包含課程名稱、短講題描述、術語清單；套用前可預覽，能編輯及回復，不覆寫其他轉錄設定。
2. 先從少量關鍵詞開始，避免塞入完整講義。提示受 tokenizer／模型文字上下文限制；應依實際 tokenizer 提醒長度，不以中文字數冒充 token 上限。
3. MLX 若要把術語加入 prompt，必須明確告知並提供選擇；不可默默改變現在的熱詞含義。
4. 保留「強制繁體中文」的輸出後處理優先權。提示只是引導，不能替代 OpenCC，也不能因套用範本就改變輸出語系。
5. 不做全文強制同音替換，以免改錯一般詞彙；使用本次的待校對提醒協助老師檢查。

## 實作前評估方式

同一組短教材比較不使用範本、短提示、提示加術語三種設定；分別使用 CPU／CUDA 標準與批次、MLX。核對專有名詞命中、其他字詞誤改、無聲段幻覺、字幕起訖與耗時。這是待執行的範本研究驗證，不把不同後端支援程度視為相同，也不保證一定提速或提準。
